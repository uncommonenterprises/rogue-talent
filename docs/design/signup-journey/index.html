Design principles applied

One primary action per screen

Every screen has exactly one cobalt rt-btn--primary. Everything else is secondary or ghost, including on the busiest screens (rates, review).

Progressive disclosure

Sign-up asks for the minimum; business/attribute detail moves to dedicated steps after the account exists. Mirrors the wizard split already shipped for models, extended to clients.

Always a next step, never a dead end

Pending, Approved and Rejected all carry one clear action: verify now, or fix and resubmit, instead of leaving the user waiting with nothing to do.

Honest trust signals

Every claim in this journey (100% of rate, one flat 15% fee, ID/bank verification, manual review) is true today per safety-framework-v1-scope.md and the account-status-lifecycle spec. Nothing borrowed from a future roadmap, no invented stats (RT-FB-09).

No stock photography

Every image slot uses the design-system diagonal-stripe placeholder, labelled, so it's unmistakable where real photography goes (RT-FB-01's fern-photo complaint, solved for good).

One learned pattern, reused

The split auth shell, the wizard stepper, and the status-card layout each appear multiple times with the same structure. A model and a client shown the same pattern once each need less onboarding of their own.

Open questions for Neil

1. Move company registration number off the sign-up form?

Screens 03 + 18 design a split where only company name is asked at sign-up, and registration number (plus industry/website/VAT) moves to a new "Your business details" step afterwards. Today's config (configUser.js) has company_registration_number set to show at sign-up already. If this split is approved, it's a real config change for the Developer, not just a new screen.

PM recommends: yes. A shorter first form means more clients finish signing up, and we still get the number before anyone can book, because approval depends on it.

2. Confirm the "confirmation on arrival" pattern for email verification

Screen 05 proposes a dismissible success banner on whichever destination the user lands on (profile wizard for models, search for clients) rather than a standalone "you're verified" page, plus a pre-filled login for the no-session case (RT-FB-07). Is this the direction to build, or would a dedicated interstitial page be preferred?

PM recommends: the banner. It confirms what happened without adding a click, and it fixes the silent redirect you flagged in RT-FB-08.

3. Is a client-side "Not approved" screen needed?

The set only specifies a model "Not approved" screen (17). Clients can equally fail review (for example a failed Companies House check). Worth confirming whether that needs its own design or can reuse screen 17's structure with client-specific copy.

PM recommends: reuse screen 17's layout with client wording ("Your business wasn't approved this time", "Update your business details"). No separate design round needed.

4. Should there be a minimum portfolio photo count before submitting?

Screen 10 has no upload minimum, but the approval review exists specifically to check portfolio quality (account-status-lifecycle §2). Worth deciding whether "Submit for approval" should require a minimum number of photos.

PM recommends: a minimum of 3 photos. Enough to judge quality and range, low enough not to put off newer models. It also saves your review time on half-finished profiles.

Resolved by PM: can a reviewer attach a reason when declining? (screen 17)

Yes. The operator can edit a user's private admin data in Sharetribe Console, so the Developer will add a "reason for decline" field there that screen 17 reads and shows. If no reason is entered, the screen falls back to a general line inviting the model to get in touch. No decision needed from you.
