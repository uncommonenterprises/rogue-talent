Design principles applied

One primary action per screen

Every screen has exactly one cobalt rt-btn--primary. Everything else is secondary or ghost, including on the busiest screens (rates, review).

Progressive disclosure

Sign-up asks for the minimum; business/attribute detail moves to dedicated steps after the account exists. Mirrors the wizard split already shipped for models, extended to clients.

Always a next step, never a dead end

Pending, Approved and Rejected all carry one clear action: verify now, or fix and resubmit, instead of leaving the user waiting with nothing to do.

Honest trust signals

Every claim in this journey (100% of rate, one flat 15% fee, ID/bank verification, manual review) is true today per safety-framework-v1-scope.md and the account-status-lifecycle spec. Nothing borrowed from a future roadmap, no invented stats (RT-FB-09).

No stock photography

Every image slot uses the design-system diagonal-stripe placeholder, labelled, so it's unmistakable where real photography goes (RT-FB-01's fern-photo complaint, solved for good).

One learned pattern, reused

The split auth shell, the wizard stepper, the status-card layout and the progress tracker each appear multiple times with the same structure. A model and a client shown the same pattern once each need less onboarding of their own.

Mobile pass (29/09/2026)

Every screen was approved on desktop on 29/09/2026. These mockups are the spec for mobile too, so all 20 were checked at 375px. Nothing scrolled sideways, but two things needed fixing, plus one small defensive tweak found while checking the rest:

  • H. Auth screens 01-07 (the split shell): below 900px the dark ink panel used to stack above the form at full height (headline, lede, three bullet points, footer), pushing the form below the fold. It now collapses to a slim ink header bar - the "Rogue." brand and a short eyebrow only - so the form starts near the top of the screen. Any useful panel-footer link (e.g. "Not a model? Sign up as a client") is duplicated under the form on screens 02, 03 and 06, next to the existing "Already have an account?" line, so no navigation is lost. Desktop (900px+) is unchanged.
  • I. Screen 18, Business type: at 375px "Sole trader or self-employed" was wrapping onto two lines inside its half-width segment, making each option ~61px tall and cramped. Below 480px the segmented control now stacks as two full-width rows instead, on both cards on the screen. 480px and up is unchanged.
  • J. Screen 10, Your portfolio: the empty state's footer (Back, plus a "0 of 3 minimum" hint next to the disabled Continue button) was tight at 375px. .wizard-actions now allows wrapping as a safety net, so it would break cleanly onto two lines rather than crowd if a phone ever runs short on room - no visible change anywhere it already fits.

Decisions (Neil, 29/09/2026)

1. Company registration number moves off the client sign-up form

Screens 03 + 18 design a split where only company name is asked at sign-up, and registration number (plus industry/website) moves to a new "Your business details" step straight after sign-up. Today's config (configUser.js) has company_registration_number set to show at sign-up already, so this is a real config change for the Developer, not just a new screen.

Decided by Neil, 29/09/2026: approved.

2. The "confirmation on arrival" pattern for email verification

Screen 05 designs a dismissible success banner on whichever destination the user lands on (profile wizard for models, search for clients) rather than a standalone "you're verified" page, plus a pre-filled login for the no-session case (RT-FB-07).

Decided by Neil, 29/09/2026: approved.

3. The client-side "Not approved" screen

Clients can equally fail review (for example a failed Companies House check). Screen 17 now shows a second status card, labelled "Client variant", below the model version, using the same structure with business wording, rather than a separate design.

Decided by Neil, 29/09/2026: approved.

4. Minimum portfolio photo count before submitting

Screen 10 has a minimum of 3 photos before "Continue" is enabled, with a "0 of 3 minimum" counter and hint shown in the empty state. Enough to judge quality and range, low enough not to put off newer models, and it saves review time on half-finished profiles.

Decided by Neil, 29/09/2026: minimum of 3 photos, approved.

5. Resolved by PM: can a reviewer attach a reason when declining? (screen 17)

Yes. The operator can edit a user's private admin data in Sharetribe Console, so the Developer will add a "reason for decline" field there that screen 17 reads and shows. If no reason is entered, the screen falls back to a general line inviting the model to get in touch. No decision needed from Neil.
