# Config-as-code (Tier 1) — status

**19 September 2026.** Groundwork for building the future LIVE marketplace identically from Git
rather than hand-clicking a second Console. Companion to `docs/config-as-code-hand-list.md` (the
planning list of what's code vs scripted vs manual) and `docs/path-to-live-v1.md` (workstream 5).

This pass is **audit + read-only export + apply plan**. It made **no writes to any marketplace**.
All exports are from the TEST marketplace `ndstealth1-test`.

---

## 1. The three mechanisms (what can and can't be captured)

| Config category | Read mechanism | Write/apply mechanism | Verdict |
|---|---|---|---|
| Transaction processes + email templates | `flex-cli process pull` | `flex-cli process push` (per env) | **Code + scripted** — already in Git under `ext/transaction-processes/`. |
| Search **index** schema (makes public-data keys filterable) | `flex-cli search` (read) | `flex-cli search set/unset` (per env) — **but only for code-defined fields; Console-defined fields are auto-indexed and "Can not be edited with the CLI"** | Scripted per env, with a caveat (see §4). |
| Listing types / listing fields / user types / user fields / access control / branding / localization / min-tx-size / layout / search-UI | **Asset Delivery API** (read-only) — `sdk.assetByAlias` | **None.** No public write API/CLI. Edited only in Console no-code UI, or superseded by code in `src/config/*.js`. | **Exported as spec (this pass). No auto-apply — see §3/§4.** |
| App copy (`en.json`), landing pages, routing, client-side process map | n/a — authored in repo | deploys with code | **Already fully in Git.** |
| Stripe, social login, domain, env-var secrets, Google Maps key | n/a | Console + env vars, per env | **Irreducibly manual per env** (bucket C of the hand-list). |

The key finding: **the no-code config assets (listing types/fields, user types/fields, etc.) can be
READ but not WRITTEN via any API/CLI.** So "config as code" for them means one of two things —
either a documented spec that a human reproduces in the live Console, or porting the definitions
into `src/config/configListing.js` + `configUser.js` so they ship with the code. Both are covered
below.

## 2. What is now captured in Git (this pass)

Exported read-only into **`config/assets/`** (see that folder's README for the file-by-file table):

- `listing-types.json`, `listing-fields.json`, `listing-search.json`
- `user-types.json`, `user-fields.json`
- `access-control.json`, `localization.json`, `minimum-transaction-size.json`
- `branding.json`, `layout.json`, `footer.json`
- `SEARCH-SCHEMA.snapshot.txt` (the server-side search index, `flex-cli search` output)

Generated by **`scripts/export-config-assets.js`** (re-runnable; `git diff` shows drift).

**Why `config/assets/` and not `ext/config/`:** `ext/` in this repo is specifically the Flex-CLI
transaction-process working tree (`ext/transaction-processes/`), the one place with a real
push mechanism. These asset exports have **no** push mechanism and are a different kind of artifact
(read-only snapshots / spec), so mixing them under `ext/` would wrongly imply they're CLI-pushable.
A top-level `config/` (build tooling already lives there) keeps them clearly separate from the
push-managed `ext/` tree. Open to relocating if the PM prefers a single `ext/config/` home.

Already in Git before this pass (unchanged): `ext/transaction-processes/` (incl. `booking-v2`),
`src/translations/en.json`, `src/config/*.js`.

## 3. Apply-to-live plan (per item) — [NEIL runs at live-build time]

When the live marketplace exists, reproduce config in this order. Every command below is a
**write to a marketplace = a money/config escalation**; they are Neil's to run, not an agent's.

### B. Scripted (one command per env)
1. **Transaction processes** — for each process in `ext/transaction-processes/`:
   `flex-cli process push --path ext/transaction-processes/booking-v2 --process default-booking -m <LIVE_ID>`
   then create/point the alias:
   `flex-cli process create-alias --process default-booking --version <N> --alias release-1 -m <LIVE_ID>`
   (Email templates travel inside the process push.) Repeat for any other processes actually used.
2. **Search index schema** — only needed for fields **not** defined via Console no-code (see §4).
   Per code-defined public key: `flex-cli search set --key <key> --type <type> --scope public -m <LIVE_ID>`.
   Verify with `flex-cli search -m <LIVE_ID>` and diff against `config/assets/SEARCH-SCHEMA.snapshot.txt`.

### A'. No-code config assets — reproduce from the exported spec
No CLI push exists. Two options (decide before live build):
- **Option A (recommended, true config-as-code):** port the definitions in `config/assets/*.json`
  into `src/config/configListing.js` (listing types + fields) and `src/config/configUser.js`
  (user types + fields), and flip the merge so **code is the source of truth**
  (`mergeDefaultTypesAndFieldsForDebugging` in `src/util/configHelpers.js`, currently `false`).
  Then both envs get identical field/type config on deploy — the correctness win. Caveats in §4.
- **Option B (interim, spec-driven manual):** keep Console as source of truth; a human recreates
  each listing type, listing field, user type, user field, access-control toggle, branding value,
  localization and min-tx-size in the **live Console**, using `config/assets/*.json` as the exact
  checklist. Faster now, but retains drift risk between the two Consoles.

### C. Irreducibly manual per env (from the hand-list, unchanged)
Stripe Connect (live account + KYB), env-var secrets (SDK client id/secret, Integration app,
Stripe publishable key, **Google Maps key + referrer restriction**, marketplace root url, Sentry),
social login client ids/secrets + redirect URIs, custom domain + DNS (SPF/DKIM/DMARC),
transactional email provider. Budget 1–2 days + verification.

## 4. Mechanism blockers / caveats found

1. **No write API for no-code config assets.** Confirmed: `flex-cli` 1.16.0 has no
   listing-fields/user-fields/listing-types command, and the Asset Delivery API is read-only. This
   is why §3 A' needs a strategy decision rather than a push command.
2. **Console-defined fields can't be CLI-search-set.** `flex-cli search` reports every current
   field as *"A listing field defined in Console. Can not be edited with the CLI."* Console
   auto-manages the search index for its own no-code fields. If we go **Option A** (code-defined
   fields), the search index for those keys becomes our responsibility via `flex-cli search set`
   per env. If we stay **Option B** (Console fields), Console handles indexing but per env, by hand.
   The two strategies therefore diverge on search too — pick one and be consistent.
3. **Merge precedence.** In `mergeListingConfig`/`mergeUserConfig`, even with the debug toggle on,
   the merge is `union(hosted, default, key)` — **hosted (Console) wins** on key collisions. So
   Option A isn't just flipping a boolean; to make code truly authoritative you must ensure the
   live Console does **not** also define the same keys (or invert the precedence). Flag for the
   PM: this is a real code change that needs testing on the test env before it's trusted for live.
4. **Process-tree drift (minor, noted not fixed).** The live-vs-git process names differ from the
   marketplace list: `ndstealth1-test` currently has `booking-v2-validation` and `default-download`
   processes that are **not** in `ext/transaction-processes/`, and Git's `booking-v2` folder maps to
   the marketplace's `default-booking` (v2) via the `release-1` alias. Worth a `process pull`
   reconciliation pass so `ext/` matches what's actually live on test before it's used as the live
   source. Out of scope for this read-only pass.
5. **404 assets** (`listing-categories`, `top-bar`, `analytics`, `google-search-console`) are simply
   not configured in this marketplace — nothing to capture.

## 5. Recommended next step

1. **PM/Neil decide Option A vs B** for the no-code assets (§3 A'). Recommendation: **Option A** —
   it's the only one that delivers the correctness guarantee `path-to-live-v1.md` is asking for
   (identical, diffable config across envs). Option B is a stopgap.
2. If Option A: do it as a **separate, tested code change** — port `config/assets/*.json` into
   `configListing.js`/`configUser.js`, resolve the merge-precedence issue (§4.3), verify the test
   env renders/searches identically, then it ships to live for free on deploy.
3. **Reconcile the process tree** (§4.4) with a `process pull` pass so `ext/` is the true source.
4. Keep `scripts/export-config-assets.js` as a **drift check** — re-run and `git diff` before any
   live build to confirm test config hasn't changed underneath us.
